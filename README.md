# 🛡️ UPI SENTINEL AI
**Intelligent Digital Payment Fraud Detection & Risk Intelligence**
*AI-Powered UPI Fraud Detection and Risk Analysis System Using Machine Learning* — B.Tech (CSE – Data Science & AI) major project.

> **Read this first (honest scope).**
> * This is an **academic decision-support system**. It never connects to a bank / UPI rails and never blocks or initiates a payment.
> * It is trained on **synthetic data**. The default dataset is generated by `dataset/generate_sample_data.py` (UPI-*style*). The optional **PaySim** dataset is synthetic **mobile-money** data — **it is not UPI data**. Metrics here do **not** predict real-world fraud performance.
> * No real UPI IDs, PINs, OTPs, or bank credentials are collected or stored.
> * Risk bands (Low 0–30 / Medium 31–70 / High 71–100) are **project-defined**, not an official banking/NPCI standard, and are configurable.

## 6. Machine-learning module

**Dataset.** `dataset/generate_sample_data.py` creates 30,000 synthetic UPI-style rows (~4 % fraud). Labels come from a hidden logistic risk model **plus noise**, so classes overlap (not trivially separable). It encodes *assumptions* (night-time activity, balance drain, new payees/devices, collect-request scams, empty receivers). `--rows`, `--fraud-rate`, `--signal`, `--seed` are configurable.

**PaySim (optional).** Download *PaySim* from Kaggle, save as `dataset/paysim.csv`, then `python run.py train --source paysim`. Mapping (see `ml/preprocessing.load_paysim`): `hour = step % 24`; `sender/receiver balance = oldbalanceOrg/oldbalanceDest` (**pre**-transaction); frequency = prior transactions by the same sender; device/session signals don't exist in PaySim and are set to 0. `newbalanceOrig/newbalanceDest` are **dropped** because they are post-transaction (leakage). All fraud rows are kept and legit rows down-sampled to ≤200k rows.

**Preprocessing.** Duplicate removal; rows missing amount/type/label dropped; other missing numerics → 0 (fixed constants, so nothing leaks from test data); range validation; fixed one-hot encoding of 7 transaction types; engineered features (log-amount, amount-to-balance ratio, night flag, empty-receiver flag). **One function, `build_features()`, is used by training *and* prediction → identical processing and column order** (`FEATURE_COLUMNS`, verified by tests and stored in metadata).

**Leakage control.** Inputs are only facts known when a payment is analysed. No label-derived or post-transaction information. Imbalance is handled with class weights (`class_weight` / `scale_pos_weight`) inside training only — no resampling touches validation/test data.

**Training & selection.** Stratified 70/15/15 train/validation/test. Four candidates (Logistic Regression, Decision Tree, Random Forest, XGBoost if installed). The decision threshold of each model is tuned for **F1 on the validation set**; the model with the best **validation F1** (balancing precision and recall) is selected; **test-set** numbers are reported once.

**Results of the run included in `models/`** (test set, 4,500 rows, 180 frauds; XGBoost not installed in the build sandbox):

| Model | Accuracy | Precision | Recall | F1 | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|---|
| **Logistic Regression ★** | 0.9453 | 0.3922 | 0.6667 | 0.4938 | 0.9413 | 0.5294 |
| Decision Tree | 0.9442 | 0.3198 | 0.3500 | 0.3342 | 0.8035 | 0.2629 |
| Random Forest | 0.9307 | 0.2988 | 0.5444 | 0.3858 | 0.9181 | 0.3882 |

Confusion matrix of the selected model: TN 4134, FP 186, FN 60, TP 120. **Be ready to explain:** (a) accuracy is misleading at 4 % fraud, hence precision/recall/PR-AUC; (b) Logistic Regression wins here partly because the *synthetic generator is itself logistic-shaped* — on real data tree ensembles often win; run `pip install xgboost` and retrain to include XGBoost; (c) precision ≈ 0.39 means many alerts are false positives — typical when recall is prioritised and why this is a *decision-support* tool.

**Risk score.** `risk_score = round(fraud_probability × 100)`. `Suspicious` ⇔ probability ≥ the tuned decision threshold (≈ 0.84 for the shipped model, i.e. score ≥ 84 → always in the High band). Because class weights inflate probabilities, treat the score as a *ranking/risk index*, **not a calibrated real-world probability**. Bands: Low 0–30, Medium 31–70, High 71–100 (`RISK_LOW_MAX`, `RISK_MEDIUM_MAX`). "High-risk" (score > 70) can therefore include transactions the classifier does not label *Suspicious* — both views are shown.

**Anomaly detection.** Isolation Forest (unsupervised, 5 % contamination) is fitted on training features only. On the test set it flagged 241 transactions (precision 0.26, recall 0.34) vs. the classifier's 306 flags (precision 0.39, recall 0.67); 107 were flagged by both. Anomalies are displayed separately and described as *unusual*, never as *fraud*.

## 7. Explainable AI
* **Global:** mean |SHAP| (tree models + `shap` installed) → otherwise **permutation importance** (the shipped result, because Logistic Regression was selected).
* **Local:** SHAP `TreeExplainer` for Decision Tree / Random Forest / XGBoost → otherwise **group-occlusion on log-odds** (replace a feature group with its training median and measure the change). Related features (e.g., amount & log-amount) are explained together.
* Every explanation reports which method produced it, plus plain-language sentences ("The payment is 96 % of the sender's balance, which resembles an account being drained").
* SHAP code paths could not be executed in the build sandbox; they are wrapped in `try/except` and fall back automatically.

## 8. REST API

| Method & path | Auth | Purpose |
|---|---|---|
| `GET /` · `GET /health` | – | info · service/DB/model status |
| `POST /auth/login` · `POST /auth/register` · `GET /auth/me` | – / – / token | JWT login; self-registration creates **role=user only** |
| `POST /predict` | token | analyse one transaction (stores it) |
| `GET /transactions` · `GET /transactions/{reference}` | token | history with filters (`search,risk_level,transaction_type,prediction,date_from,date_to,anomaly_only,limit,offset`) · detail + explanation |
| `GET /analytics` | token | KPIs & chart data computed from stored rows |
| `GET /model/performance` | token | metrics, curves, importance, anomaly comparison |
| `GET /anomalies` · `GET /risk/config` | token | Isolation-Forest anomalies · risk bands |
| `GET /admin/stats` | **admin** | users, monitoring, model & DB stats |

**Request** (only the first four fields are required; others default to typical low-risk values that are echoed back in `assumed_defaults`):
```json
{ "amount": 25000, "transaction_type": "P2P", "transaction_hour": 23, "transaction_frequency": 8,
  "sender_balance": 40000, "receiver_balance": 0, "device_risk_score": 0.6,
  "is_new_device": true, "is_new_payee": true, "failed_attempts_24h": 2 }
```
**Response** (values are produced by the trained model; abridged): `transaction_id, prediction, fraud_probability, risk_score, risk_level, anomaly{is_anomaly, anomaly_score}, model_name, explanation_method, summary, top_factors[...], assumed_defaults, timestamp`.

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:8000/auth/login -H "Content-Type: application/json" \
        -d '{"username":"admin","password":"Admin@12345"}' | python -c "import sys,json;print(json.load(sys.stdin)['access_token'])")
curl -X POST http://127.0.0.1:8000/predict -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"amount":25000,"transaction_type":"P2P","transaction_hour":23,"transaction_frequency":8}'
```
**Postman:** import `postman/UPI_Sentinel_AI.postman_collection.json`, run **POST /auth/login** first (a test script stores the token in `{{token}}`), then any other request. **Swagger:** open `/docs` → *Authorize* → paste the token.

Status codes: 200/201 success · 401 not authenticated · 403 not admin / registration off · 404 unknown reference · 409 duplicate user · 422 validation · 429 too many login attempts · 503 model missing · 500 generic (no internals leaked).

## 9. Database
SQLite file `upi_sentinel.db` by default. Tables: `users` (hashed passwords, role), `transactions` (reference + numeric features, optional ground-truth `actual_label` for seeded data, `source`), `prediction_history` (prediction, probability, risk score/level, anomaly flag/score, explanation JSON), `model_performance`.
**MySQL:** `pip install pymysql`, create an empty database, set `DATABASE_URL=mysql+pymysql://user:password@host:3306/upi_sentinel` in `.env`, restart — tables are created automatically.

## 10. Security summary
PBKDF2-HMAC-SHA256 (310k iterations, per-user salt) — no plaintext passwords · JWT with expiry, `SECRET_KEY` from the environment (API refuses to start without a ≥32-char key) · role-based access (`require_admin`) enforced server-side and in the UI · per-user data isolation · Pydantic validation with `extra="forbid"` · SQLAlchemy bound parameters only · login throttling (5 failures / 5 min per username, in-memory) · CORS limited to `FRONTEND_ORIGINS` · no PIN/OTP/UPI-ID/credential fields exist anywhere · generic 500 errors. *Not covered (out of scope for a student project):* HTTPS termination, refresh tokens, persistent/distributed rate limiting, audit logging.

## 12. Deployment notes
* **Dashboard → Streamlit Community Cloud** (main file `frontend/dashboard.py`; set secret/env `API_BASE_URL` to your public API URL). **API → Render / Railway / Fly.io / PythonAnywhere**: start command `uvicorn backend.main:app --host 0.0.0.0 --port $PORT`; build command `pip install -r requirements.txt && python run.py train`. Set env vars: `SECRET_KEY`, `ADMIN_*`/`DEMO_*` (strong values), `FRONTEND_ORIGINS=https://<your-dashboard-url>`.
* **Database persistence:** free tiers usually have an **ephemeral filesystem** — a SQLite file is wiped on redeploy/restart. For anything you want to keep, use a managed MySQL/PostgreSQL (set `DATABASE_URL`; for PostgreSQL install `psycopg2-binary`).
* **Free-tier limits:** services sleep after inactivity (first request is slow), small RAM (skip `shap` or reduce trees if you hit memory limits), limited CPU/build time (use `python run.py train --quick`), public URLs need HTTPS (the platforms provide it). Train on the build step or commit `models/` built with the *same* scikit-learn version.
* Seed demo data on a hosted instance with `python run.py seed` (a shell/one-off job).

## 15. Known limitations (say these before the examiner does)
Synthetic data only · risk score is not a calibrated probability · precision is modest (many false alerts) · transaction frequency is user-supplied (a real system would compute it from history) · single-model, no concept-drift monitoring or retraining pipeline · in-memory login throttle · SHAP/XGBoost paths untested in the build sandbox · dashboard visuals could not be screenshot-verified in the build sandbox.

## 16. Viva quick answers
* **Why Random Forest / XGBoost / LR?** Compared on the same split; selection by validation F1, test set untouched until the end.
* **Why not accuracy?** 96 % accuracy is achievable by predicting "genuine" always.
* **How is leakage prevented?** Only pre-transaction inputs; post-transaction balances dropped; thresholds/model chosen on validation; class weights only on train; fixed (not data-derived) imputation constants.
* **Why train/predict mismatch can't happen?** Both call `build_features()` and use `FEATURE_COLUMNS`; the predictor refuses a model whose stored columns differ.
* **Supervised vs anomaly detection?** Supervised learns known fraud patterns; Isolation Forest finds statistically rare behaviour (could catch novel fraud, but also flags rare legitimate payments).
* **Is it real UPI?** No — synthetic; PaySim is mobile-money; this is decision support only.
